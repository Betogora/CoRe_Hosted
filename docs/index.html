Pflege #

  1. Eine Änderung nur in der Quelle ihrer Rolle vornehmen; andere Dokumente verlinken.
  2. UI-Änderungen in den App-Quellen umsetzen und die betroffenen Demos in scripts/uiCatalogDemos.tsx bzw. scripts/uiCatalogPatterns.html mitziehen.
  3. npm run docs:build erzeugt die Leseseiten, npm run check:docs prüft Quellenstand, Verweise, Journey-Regeln und die Zuordnung aller exportierten UI-Komponenten zu Demos. HTML-Dateien nie direkt bearbeiten.
  4. Sichtbare Änderungen nach der visuellen Pflichtmatrix ansehen; ein technischer Check ersetzt das nicht.
  • Schaubilder stehen als schaubild-Codeblock im Markdown: Titel:, dann Zeilen aus Kästen als Folge: (mit Pfeilen) oder Gruppe: (nebeneinander), dazwischen Pfeil: nach unten. Ein Kasten ist Titel | Detail, wahlweise mit Ton davor ([primär], [erfolg], [warnung], [gefahr], [info]); -> Text beschriftet den nächsten Pfeil einer Folge.
  • Erledigtes verschwindet aus todo.md; Details stehen in Commit und Pull Request, Production- und Datenbankschritte als Betriebsnachweis in history.md.
  • Offene Gestaltungsvarianten werden per visual-ab-review als temporäre Vergleichsseite vorgelegt und danach gelöscht.
  • Historische Roadmaps, Audits und Zwischenstände bleiben nur in Git.
  • npm run mascots:build erzeugt den lokalen Maskottchen-Vorrat unter output/mascots/ (nicht im Repository); das App-Logo entsteht in docs:build.

Wann ein ADR entsteht #

Nur wenn alle drei Punkte zutreffen:

  • Die Entscheidung betrifft mehrere Module oder Bereiche oder ist schwer umkehrbar (Datenmodell, Persistenz, Sicherheit, Anbieter, Kosten, Datenschutz).
  • Ihr Grund steht weder im Code noch in den Specs, weil er Alternativen abwägt.
  • Ohne Festhalten würde sie wahrscheinlich erneut diskutiert oder versehentlich umgekehrt.

Ändert sich eine Entscheidung, wird ihr Text aktualisiert; eine aufgehobene wird gelöscht. Nummern bleiben stabil.
